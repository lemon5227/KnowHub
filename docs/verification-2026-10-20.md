`codex/enterprise-workflow` 的新引擎；旧 `backend/` 不是本次验收对象。本地 macOS、Python3.12、PostgreSQL17/pgvector容器、CPU上的 `intfloat/multilingual-e5-small`（384维）、DeepSeek `deepseek-flash` 非思考模式原生 Function Calling、React/TypeScript 工作台。

## 真实模型与向量

真实多语言向量模型输出shape为 `(1,384)`，通过pgvector实际查询，并在模型回答中回溯到原文。

公开保留全部实际输出，不只保留成功案例：

| 文件 | 内容 |
| --- | --- |
| `initial-live-run.json` | 首次真实规范问答，2次模型调用，来源可回溯 |
| `live-capabilities.json` | 第一轮4题×2模式，保留订单查询的引用校验失败 |
| `business-read-after-fix.json` | 引用格式处理后复测订单查询；真实取得delayed/48小时，但末尾仍错误地把历史已保存备注解释为待确认建议 |
| `verified-capabilities.json` | 第二轮4题×2模式；规范与缺政策题完成，业务查询取得真实数据；更新题在工单已被UI处理为in_progress后选择先询问是否追加备注，机械检查仍记False |
| `stage-and-reject-after-fix.json` | 明确请求追加备注后生成待确认建议，实际拒绝与重复拒绝，前后工单完全相同 |
| `final-browser-approval.json` | 最终版本浏览器真实发起1次运行/1次批准；3次模型调用，v2→v3、审计1条；后续GET核查与重载结果 |
| `pdf-ingestion-smoke.json` | 真实PDF上传，文字与第1页元数据正确，0次模型调用 |

这组检查比较的是**可用能力**：单次文档RAG没有订单数据库和写工具，因此不能完成业务数据核实或变更建议。它不是GraphRAG论文复现，不是纯检索算法比较，也不支持“准确率提升X%”或生产成功率的结论。

机械检查要求预先指定的工具、状态、引用和关键事实；它不等同完整语义评分。第一轮后追加了“失败/耗尽不能算拒答成功”的检查，并统一组合引用解析。第二轮更新题记录为False没有改判：工单状态已变化，模型做了额外澄清，这一状态敏感边界需要保留，而非隐藏。

工具返回的是数据库事实，但模型仍可能误解业务字段或输出不必要的澄清。来源ID检查也只证明引用存在，不证明逐句蕴含。现在没有跨场景泛化、长期稳定性、大规模容量或真实用户效益证据；简历不写这些指标。

## 审查与修复

独立后端审查确认并已修复：

1. 工具节点提前发布待确认状态，最终保存可能覆盖并发审批。现在只在最终快照发布可审批状态；回归在每次发布时立即批准，验证只发布一次并保持completed。

3. 评测曾把“无法访问模型”或“调用耗尽”误作未知政策拒答成功。现在非变更任务必须先满足completed；组合来源解析与Agent一致。
