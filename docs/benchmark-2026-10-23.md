# KnowHub enterprise-v1 实测报告（2026-10-23）

本轮把检索与业务任务分开计分。**27份合成文档 / 81个片段 / 60道检索题**上，混合检索 Recall@5 为 **100.0%**，纯向量为 **96.7%**；**24个真实 DeepSeek Agent 用例的任务成功为16/24（66.7%）**。8个更新用例没有生成结构化待审批提案，全部失败。检索分数不能代替端到端成功率。

这些是本项目自建、公开、开发者编写的有限合成评测，不是企业线上成绩、外部盲测、独立人工双标或真实客户使用数据。所有问答/运行都保留；没有按成功筛选、重跑取最好值，评测过程中没有改产品算法或提示词。

## 1. 固定题集与环境

- 题集在观察排名/模型输出前提交：`ca38ff2`；引擎在原有实现 `33c1c6b` 上未修改。首次评测脚本提交 `fe5ea2d`。后续仅修正标注/完善离线报告，不更改运行输出。
- 27份知识文档：24份新编合成企业规范和3份原有演示SOP；生产切分后81片段。60题包括44道改写题、4道编号题、12道多证据题。未包含真实扫描PDF、表格、长文档、大规模语料、并发或复杂跨文档推理测试。多证据题主要组合同一政策的不同章节。
- 24个工单用例、7类任务；每例独立初始工单、订单。8个延迟更新例使用相同指令模板、不同编号/延迟小时数，不能当作8种独立业务流程。4个未知政策题是明显虚构的星际业务，拒答难度有限。
- macOS / Apple M4；Python3.12.14；PostgreSQL17.11 + pgvector（aarch64容器）；E5在CPU实际推理；`intfloat/multilingual-e5-small` revision `614241f622f53c4eeff9890bdc4f31cfecc418b3`。实际依赖版本见原始JSON环境字段及uv.lock。
- 模型配置为 `deepseek-flash`、temperature=0、每请求最多1200输出Token、每任务最多4次请求。供应商别名底层版本未由当前封装返回，未固定供应商权重版本。
- 新评测请求上限96，实际59，失败请求0，总Token **99,060**。不含此前2026-10-20的40次验收请求。没有额外评委模型调用；费用未按未经确认的缓存价格折算成人民币。
- 使用单独 `knowhub_benchmark` 数据库，不清理演示库。最终24个工单均为v1、审计0条。

## 2. 检索：相同数据、相同查询、现有生产实现

三种方法均调用现有 `Retriever.search(query,k=8,mode=...)`：E5+pgvector精确余弦、BM25中文字/双字及拉丁标识符、两路RRF(k=60)。没有为结果调权、加Reranker或更换模型。每题按dense/lexical/hybrid顺序各跑一次；只有一次预热查询，不计入分数。

| 方法 | Recall@1 | Recall@3 | Recall@5 | Recall@8 | MRR@8 | 检索P50 / P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 纯向量（dense） | 79.44% | 94.44% | 96.67% | 100.00% | **0.9454** | 19.08 / 22.42 ms |
| BM25（lexical） | 74.72% | 93.61% | 97.78% | 97.78% | 0.9047 | **8.70 / 11.34 ms** |
| 混合检索（hybrid） | 78.06% | **96.94%** | **100.00%** | 100.00% | 0.9422 | 25.29 / 28.76 ms |

- Recall@k：每题前k个不重复片段中的已标注相关片段数 / 该题已标注相关片段总数，再对60题取宏平均；不是“答对题数/总题数”。相关片段由精确来源+章节标注解析到实际生产chunk ID。勘误后共77个query–chunk正例关联，允许相近原文提供重复支持；这不是对所有可能语义相关段落的独立穷尽标注。
- MRR@8：首个相关片段倒数排名，未进入前8计0。Hit@5：至少命中一条标注证据；dense/BM25为59/60，hybrid为60/60。前5覆盖所有标注正例的题数分别为57/60、58/60、60/60；重复支持也算标注正例，因此不等同回答所需最小证据是否齐全。
- 当前产品k上限8，本轮没有Recall@10。延迟包含查询embedding、数据库读取、BM25和融合；不含模型加载、文档embedding、网络LLM和回答生成。串行热缓存单机结果不是服务SLA，方法顺序也未随机化。
- hybrid在本题集的Recall@5比dense高**3.33个百分点**，但MRR@8略低、延迟更高；不能写成“全面优于向量检索”或“准确率提升3.33%”。仅有3题的全部正例覆盖从失败变成功，未据此声称统计显著或生产泛化。

### 标注勘误：保留原始分数与原始排名

第一次题集有一个章节指派错误：Q029问429限流却指向认证章节。另漏标了Q004、Q007、Q009、Q049、Q052中原有SOP的等价/部分支持。完整原因逐条记录在 [`judgment-errata.json`](../benchmarks/enterprise-v1/judgment-errata.json)。原始题集/SHA256SUMS和排名文件保持不变；三种方法一律用相同更正标注离线重新计分，无新的embedding或检索调用。

| 标注版本 | dense Recall@5 | BM25 Recall@5 | hybrid Recall@5 |
| --- | ---: | ---: | ---: |
| v1原始标注（含已知错误） | 95.00% | 95.83% | 98.33% |
| v1.1勘误（本文主结果） | 96.67% | 97.78% | 100.00% |

原始在 [`retrieval.json`](../artifacts/benchmarks/enterprise-v1/retrieval.json)，勘误计分在 [`retrieval-corrected.json`](../artifacts/benchmarks/enterprise-v1/retrieval-corrected.json)，包含原始文件与勘误哈希。该过程发生于观察排名后，属于透明标注修复；不是新的未见测试集。高分很可能还受短文档、自建题集与有限难度影响，后续应另收集独立题集。

具体缺口：dense在Q006（退款超时追踪）前5未命中标注证据，Q004/Q007只覆盖部分标注；BM25在Q013（否认签收）前8未命中，Q049（不同阶段更址）遗漏部分证据。原始逐题排名全部公开。

## 3. 真实模型业务任务：成功16/24

| 任务类型 | 成功 / 总数 | 判定要点 |
| --- | ---: | --- |
| 政策问答 | 4/4 | 实际检索、关键事实和有效引用，不生成提案 |
| 当前订单核实 | 4/4 | 实际读取工单/订单、检索规范、正确事实和订单号 |
| 生成待审批提案 | **0/8** | 必须实际调用提案工具并返回awaiting_approval；文字草稿不算 |
| 未知政策 | 4/4 | 检索后说明缺依据，不给虚构业务套用金额/承诺 |
| 缺编号追问 | 2/2 | 不猜客户记录，不生成提案，要求补编号 |
| 记录不存在 | 1/1 | 两个真实查询返回不存在，如实告知 |
| 不安全结案要求 | 1/1 | 未送达不resolved、不绕过确认、不生成提案 |
| **总计** | **16/24（66.7%）** | 规则检查与逐例开发会话语义核查结论一致 |

规则在运行前固定，检查终态、必需工具、事实词、引用、提案与写入状态。随后开发助手逐条对照工具结果及原文查看回答，核查说明保存在 [`manual-review.json`](../artifacts/benchmarks/enterprise-v1/manual-review.json)。这不是独立人工盲评、完整逐句蕴含率或“零幻觉”认证。

16/24的Wilson 95%区间约46.7%–82.0%，只提示小样本不确定性；用例非随机、模板相关，不能把该区间外推成生产表现。模型服务成功返回24/24，也**不**代表任务成功24/24。

### 真实失败：多问一次确认，导致流程没有落到提案工具

W09–W16全部核实了订单和规范、给出正确的文字备注，却又问“需要我提交该提案吗？”。实际没有调用 `propose_ticket_update`、`proposal=null`、状态为completed，操作台无法按结构化提案继续审批。用户已经明确要求生成待确认提案，因此不能把安全的“不写入”当作完成任务。

这8例保留为失败，没有改问法重跑、没有用人工补建提案来补分。根因方向是模型把“准备/暂存提案”和“批准真实写入”的确认边界混淆；尚未在本轮修复/验证。下一轮应先澄清工具协议，再用新的未见表达验证，避免只适配这一个模板。

### 边界与开销

- 55次工具调用，Schema/前置条件均被接受（55/55）；这不等于工具选择正确率100%，例如W08先搜了物流规范，读订单后才改搜支付规范。W23两次“记录不存在”是预期业务返回，不能当作参数错误。
- 24/24运行前后都没有未审批写入。最终数据库24条工单版本均为1、审计0；本轮没有成功生成提案，因此**真实批准/拒绝/重复确认覆盖为0例**，不能报告审批成功率。早期独立审批验收见[2026-10-20报告](verification-2026-10-20.md)，自动化事务测试也仍单列。
- 单任务耗时P50 **5.409s**、P95 **6.833s**，包含本地工具/存储及真实LLM请求；每用例1–3次模型调用，共59次、99,060 Token。无并发压力、长尾稳定性或多轮对话泛化结论。

```bash
# 已有结果：离线复算，不访问数据库或付费模型
uv sync --locked --python 3.12
uv run python -m scripts.benchmark rescore
uv run python -m scripts.benchmark report

docker compose -p knowhub up -d db
uv run python -m scripts.benchmark retrieval --output artifacts/private/new-benchmark
```

新retrieval运行会记录本次完整片段索引；原始运行的corpus-index从同一未更改评测库导出。汇总脚本支持部分记录并标出workflow是否完整；本次为完整24例。已发布文件带SHA256清单，离线复算应得到相同指标；真实模型重跑可能不同，不能把别名+temperature=0当作位级确定性。
